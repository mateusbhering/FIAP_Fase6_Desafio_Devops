O projeto

Emissões de CO₂ de uma cidade, medidas e consolidadas

A EcoTrack API registra as emissões de gases de efeito estufa de cidades e organizações e as consolida em toneladas de CO₂ equivalente (tCO₂e), seguindo os escopos do GHG Protocol. Isso dá à gestão pública um indicador ambiental (o “E” do ESG) acompanhável.

EscopoSignificadoExemplo municipal
ESCOPO_1Emissões diretasFrota de ônibus a diesel
ESCOPO_2Energia compradaIluminação pública
ESCOPO_3Cadeia de valorColeta e aterro de resíduos

Camadas da aplicação

  • controller: REST + validação (Bean Validation), erros no padrão RFC 7807
  • service: regras e consolidação em tCO₂e
  • repository: Spring Data JPA
  • Flyway versiona o schema; o Hibernate só valida (ddl-auto: validate)
  • Actuator: /health, /readiness, /info (versão e ambiente)
  • Perfis: staging (debug, Swagger) · prod (log WARN, sem Swagger, health sem detalhes)
Pipeline CI/CD · GitHub Actions

Quatro etapas encadeadas, com um gate entre cada uma

1Build e testes

./mvnw verify compila e roda os 11 testes (unitários, web e integração) e a cobertura JaCoCo. Publica o resumo dos testes e os relatórios e o .jar como artefatos.

2Imagem Docker

Buildx com cache do GitHub Actions. Push para o GHCR com as tags <sha> (imutável) e main.

3Deploy staging

Environment staging. deploy.sh sobe o Compose, espera a readiness e roda o smoke test completo: cria, consulta, consolida e apaga um registro.

4Deploy produção

Environment production, que aceita aprovação manual. Implanta a mesma imagem e roda o smoke test somente leitura.

Lógica

  • Gatilhos: push na main roda tudo. Pull request roda só a etapa 1. Commits só de documentação não disparam.
  • Gates: teste falhou, não há imagem. Staging falhou, não há produção.
  • Build once, deploy many: produção recebe exatamente o artefato validado em staging.
  • Rollback automático: se a nova versão não fica pronta, o script volta a anterior.
  • Concorrência: dois deploys nunca rodam ao mesmo tempo (concurrency).

Segredos e alvo do deploy

  • A senha do banco vem dos secrets de cada Environment. No repositório ficam só configurações não sensíveis (deploy/*.env).
  • Servidor via SSH: com DEPLOY_SSH_* configurados, envia o Compose e os scripts para uma VM com Docker.
  • Runner do GitHub (configuração atual): o ambiente sobe no próprio runner com o mesmo Compose e o mesmo script. Valida ponta a ponta, e o ambiente é efêmero.
  • Dependabot mantém as dependências, as actions e as imagens atualizadas.
Docker · arquitetura da imagem

Dockerfile multi-stage: build pesado, runtime enxuto

# Etapa 1: build
FROM maven:3.9-eclipse-temurin-17 AS build
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn package -DskipTests \
 && java -Djarmode=tools -jar target/ecotrack-api.jar \
      extract --layers --launcher --destination target/extracted

# Etapa 2: runtime
FROM eclipse-temurin:17-jre
RUN groupadd --system ecotrack && useradd --system ... ecotrack
COPY --from=build .../dependencies/ ./
COPY --from=build .../spring-boot-loader/ ./
COPY --from=build .../snapshot-dependencies/ ./
COPY --from=build .../application/ ./
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 ..."
USER ecotrack
EXPOSE 8080
VOLUME ["/app/logs"]
HEALTHCHECK CMD curl -fsS .../actuator/health/readiness ...
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

Aprendizados

Desafios encontrados e como foram resolvidos

DesafioSolução
A imagem eclipse-temurin:17-jre-alpine não tem versão ARM64: o build falhava no Mac com Apple Silicon (no match for platform in manifest)Troca para eclipse-temurin:17-jre (multi-arquitetura) e ajuste dos comandos de usuário e healthcheck para a base Ubuntu
O Docker travava ao montar a pasta do projeto (Desktop do macOS) como bind mountO Compose passou a usar só volumes nomeados; o build envia o contexto sem depender de montagem de pasta
Maven não instalado na máquina de desenvolvimentoMaven Wrapper (./mvnw): a mesma versão do Maven no computador e no CI, sem instalação
Sem servidor em nuvem disponível para staging e produçãoWorkflow de deploy com dois alvos: SSH para uma VM ou o runner do GitHub, usando o mesmo Compose e o mesmo script
Evitar que uma versão quebrada derrube um ambienteEspera da readiness probe, rollback automático, smoke tests e gate staging → produção
Testes de integração sem depender de um PostgreSQL no CIH2 em modo PostgreSQL, rodando as mesmas migrations Flyway de produção
Senha do banco sem ir para o repositórioSecrets por Environment, senha efêmera e mascarada no runner, Compose que não sobe sem a senha
Primeira execução com avisos de actions obsoletas (Node 20) e PRs do Dependabot com saltos de versão principalActions atualizadas para as versões atuais; Dependabot configurado para ignorar migrações de versão principal (Spring Boot 4, Java 24)
